<p>“你们的日志能查吗”这句问话，背后通常是三种处境：账号出了异常想找原因、公司合规要求留痕、或者两个同事在争到底是谁改了配置。三种需求的答案不一样，因为要查的东西根本不在同一个地方。这篇把最常被问到的五个问题按顺序串起来讲，每个问题给出可核查的答案和能自己动手的补足方案。</p>

<h2>一、服务商那边到底记不记日志</h2>
<p>先泼一盆冷水：多数住宅代理服务商不会给你逐条请求记录。原因一半是技术成本，一半是隐私政策。</p>
<h3>常见能拿到的三类记录</h3>
<p>连接数与时长的聚合统计、出口的启停与替换记录、以及账单流水。这三类基本每家都有，因为计费需要。</p>
<h3>通常拿不到的两类</h3>
<p>具体的访问目标域名、以及完整的请求内容。前者涉及用户行为画像，后者涉及内容本身，正规服务商一般在隐私条款里明确不采集或短期即删。</p>

<h2>二、我能不能查到自己那条出口的登录记录</h2>
<p>这里的“登录”要区分两层：登录代理控制台，和通过代理访问目标服务。两层能查到的信息完全不同。</p>
<h3>控制台登录记录</h3>
<p>大多数平台提供登录历史：时间、来源地址、结果。用来发现异常登录很有效，建议开通登录告警邮件，成本几乎为零。</p>
<h3>通过代理的访问记录</h3>
<p>通常查不到。这时需要在你自己的设备或网关上做记录，也就是把观测点前移。这一点在合规审计里尤其关键——审计要的是你能证明自己做了什么，而不是服务商替你证明。</p>

<h2>三、自建侧还能补什么</h2>
<p>既然上游不给细粒度日志，就把能自己控制的部分做扎实。三处地方最值得下手。</p>
<h3>客户端侧</h3>
<p>在发起请求的程序里记录时间戳、出口地址、目标域名、状态码、耗时。这五项足够支撑绝大多数排障，用结构化日志（JSON 行）方便后续检索。</p>
<h3>网关侧</h3>
<p>如果有多台设备共用出口，在网关上做一次转发日志，能覆盖到客户端装不了 agent 的情况。注意只记元数据，不记请求体。</p>

<h2>四、审计要留哪些字段</h2>
<p>如果是为了应付合规检查，字段设计比日志量更重要。缺一个关键字段，整批日志的说服力都会打折。</p>
<h3>六个必备字段</h3>
<p>操作时间（含时区）、操作人、来源地址、出口地址、动作类型、结果。六项之外再加一个业务标识（比如账号 ID），就能把技术日志和业务单据对上。</p>
<h3>时间统一到 UTC</h3>
<p>跨时区团队最容易在这里翻车：三个人三个时区，日志时间对不上，事件顺序就重构不出来。统一存 UTC，展示时再转本地。</p>

<h2>五、日志留多久、怎么存</h2>
<p>留存期不是越长越好，越长责任越重。常见的做法是按用途分层。</p>
<h3>按用途定期限</h3>
<p>排障用的明细日志保留 7–30 天，够定位问题即可；审计用的操作日志保留 6–12 个月，按行业要求调整。超过期限的自动归档或删除，别让磁盘无限膨胀。</p>
<h3>三个基本防护</h3>
<p>写入后不可篡改（追加写或对象存储的合规模式）、访问需要单独授权、导出行为本身也要记录。最后一条最容易被忽略，但它恰恰是审计最想看的。</p>

<h2>常见问答</h2>
<h3>住宅代理会记录我访问了哪些网站吗？</h3>
<p>答：多数正规服务商声明不记录具体访问目标，仅保留计费所需的连接元数据。具体范围以隐私政策为准，采购前应逐条确认。</p>
<h3>没有日志是不是就不能做审计？</h3>
<p>答：不是。审计的核心是“可证明的操作链”，把观测点放在自己的客户端和网关上同样成立。上游日志是补充，不是前提。</p>
<h3>日志里能存请求内容吗？</h3>
<p>答：技术上可以，合规上要慎重。请求体可能包含个人信息或商业数据，采集应有明确目的与授权，并做脱敏与访问控制。</p>
<h3>多人共用一个账号怎么定位到人？</h3>
<p>答：给每人开独立子账号或独立密钥，日志按凭据区分。共用凭据的情况下，事后只能靠时间与来源地址推测，可靠性很差。</p>

<h2>合规提示</h2>
<p>日志的采集、存储与跨境传输应遵循当地个人信息保护法规，明确告知用途并取得必要授权，坚持最小必要原则。</p>
<p>本文不构成法律意见。涉及审计留痕的具体期限与字段要求，请咨询所属行业的合规负责人或专业机构。</p>
